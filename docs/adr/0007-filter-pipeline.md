# 0007. フィルタの段構成を一か所にまとめ、設定で変えられるようにする

- ステータス: 採用（遡って計算し直す手段は、ADR 0010のBigQueryに移った）
- 決定日: 2026-09-14
- 起票: chirushiyo
- 関連: #22, #11, #1, PR #27, ADR 0004, ADR 0008, ADR 0010

## 背景

`/aggregate`のフィルタは、順序が固定化（Appleの本体端末に絞る → 重複排除 → RSSIの閾値）され、コードに書かれていた。「Appleに限る」「RSSIの閾値は -100」という前提を確かめるための元データは、`/aggregate`のたびに削除され、後から分析できなかった。

## 決定

1. `dedupeByMac`を、型を変えず、情報を捨てずにまとめる関数にする。同じMACの中でRSSIが最大のものを代表にし、戻り値にはMACの代わりに、その集計1回限りのランダムなUUIDと検出回数を持たせる
2. 既定の順序を「重複排除 → Company ID → RSSI」にする
3. 段の構成（順序、パラメータ）をFirestoreの`config/filter_pipeline`で管理する。段の設定は、`name`で見分けるZodのdiscriminated unionで検証する
4. 実行のたびに、段ごとの件数（前と後）を記録する
5. 診断モードが有効なら、重複排除の後の集合（UUID、RSSI、Company ID、Nearby Infoの有無、検出回数）を`scan_diagnostics/{location}__{windowStart}`に保存する。MACと`rawData`は保存しない

## 理由

- 順序（決定2）: 診断データに保存するのは重複排除の後の集合。Company IDで先に絞ると、保存されるのはAppleの本体端末に絞った後のものだけになり、「Appleに限る」という前提自体を検証できない（許可リストを狭める方向しか調べられない）
- 順序を変えても結果は同じ: 重複排除（同じMACの中でRSSI最大を代表にする）と、Company ID・RSSIの条件で絞るフィルタは、同じ端末が送るCompany IDとNearby Infoが揺れない限り、入れ替えても最終的な台数が変わらない。テスト（`0086c7a`）でも確かめた
- 設定にする（決定3）: 許可リストや閾値を、再デプロイなしに調整できる。将来の管理画面は、このドキュメントを書き換えるだけでよい
- UUIDに置き換える（決定1）: 診断データから個々の端末を集計をまたいで追えないようにする

## 検討した選択肢

| **選択肢** | **採用しなかった理由** |
|---|---|
| Company ID → 重複排除 → RSSI（当初案） | 診断データがAppleに絞った後のものになり、前提を検証できない |
| 段の設定を`params: any`で持つ | 既存の水準（Zodのdiscriminated union）から外れる。存在しない段や、必須のパラメータの欠落を一か所で捕まえられない |
| 重複排除の前の、検出1件ずつをUUIDにして保存する | 重複排除のロジックそのものを変えた場合まで遡って検証できるが、今の目的（許可リストと閾値の検証）には過剰で、保存量も増える |

## 結果

- 診断データは、診断モードが有効だった期間の分しか溜まらない。Company IDで絞る前の全デバイスが対象なので、件数は多くなる
- MACアドレスがまれに衝突した場合、順序の入れ替えで結果が変わりうる
- 重複排除のロジック自体を変えた場合は、診断データからは遡って計算し直せない

issue #22の計画と、実装の違い:

| **issue #22** | **実装** |
|---|---|
| 段階1（デモ前）と段階2（デモ後、設定で変えられるようにする部分）に分ける | 両方を同時に実装した（2026-09-15） |
| 診断モードの切り替えは、暫定的に`config/diagnostics`に置き、後で統合する | 最初から`config/filter_pipeline.debugModeEnabled`に統合した |
| 設定が読めないときの扱いは未定 | ドキュメントが無い、または検証に失敗したら、従来と同じ既定の構成（重複排除 → `004C`かつNearby Info必須 → RSSI -100、診断モードはオフ）で動く |
| 重複排除を先頭に固定するか、先頭であることを検証する | 未対応。`config/filter_pipeline`で重複排除を先頭以外に置けてしまう |
| 設定を変えたとき、診断データに新しい条件を当てて過去の台数を計算し直す（決定6） | ADR 0010で生データをBigQueryに貯めるようになったため、計算し直しはBigQueryから行う方針に変わった（#41） |

ADR 0010の後は、`pending_scans`のMACは受信の時点でHMACにされている。`dedupeByMac`はハッシュ値で重複を除き、診断データにはさらにUUIDに置き換えたものを保存している。

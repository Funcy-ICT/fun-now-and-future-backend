# 0015. ノードの停止は/aggregateで判定し、停止と復旧をメールで知らせる

- ステータス: 採用（メールのアラートは未実装）
- 決定日: 2026-10-11
- 起票: chirushiyo
- 関連: #32, #35, PR #46, ADR 0009, ADR 0013, ADR 0014

## 背景

センサーが止まったことに、すぐ気づける必要がある。設計メモ2.1では生死確認を最優先とし、2.3で、停止などのアラートを管理画面に出し、メールでも送るとしていた。

今あるもの:

- `/aggregate`は、ノードごと・5分窓ごとの受信回数（`postCount`）と検出数（`totalMacCount`）を`node_health_stats`に書く。同じものを`aggregate_runs`にも送る（PR #46）
- ESP32は、検出が0件でも`devices: []`で送る（2026-10-11にファームウェアの設定を確認）。受信が無いことは、ノードか通信が止まっていることを意味する
- 基準値の設定（`config/baseline`）は、locationごとに稼働時間帯（`operatingStartHour`、`operatingEndHour`）を持つ。センサーが夜間に止まるlocationでは、ここを変える（ADR 0009、`docs/configuration.md`）
- サイネージ向けの`GET /getCongestion`は、locationの最新の記録が15分より古いと`stale`を返す（`services/congestion.ts`）

足りないもの:

- `/aggregate`が知っているのは、その窓に送ってきたノードだけ。完全に止まったノードは見えない。ノードは事前に登録しない（#32）
- 撤去したノードを、監視から外す方法
- 通知の仕組み

## 決定

1. 停止の判定は、`/aggregate`が窓ごとに行う
2. 監視するのは、一度でも送ってきたノード。`/aggregate`は、ノードごとのlocation、最終受信時刻、状態（動いている、止まっている）を、1つのドキュメント（`status/node_last_seen`。名前は仮）に書く
3. 停止とみなすのは、そのノードのlocationの稼働時間帯の中で、受信が2窓（10分）続けて無いとき。復旧は、止まっているノードから受信があったとき。稼働時間帯は`config/baseline`の値（locationごとの上書きを含む）を使い、ノードごとには持たない
4. `config/nodes`で撤去済み（`retired`）にしたノードは、判定と通知から外す。集計には影響しない。`config/nodes`には表示名も置く。どちらも管理画面から変える
5. 停止と復旧のときだけ、構造化ログを1行出す。Cloud Loggingのログベースのアラートで、メールを送る
6. `/aggregate`自体が止まったことは、`aggregate finished`のログが一定時間出ないことで知らせる
7. 管理画面の今の状態は2のドキュメントから、ノードごとの推移のグラフは`node_health_stats`から読む

## 理由

- 自動で監視に入れる（決定2）: 事前登録をやめた方針（#32）と合う。管理画面で登録したノードだけを監視すると、登録を忘れたノードは止まっても通知されない
- 1つのドキュメント（決定2）: 集計1回につき、読み取り1回、書き込みは最大1回で済む。管理画面も、1回読めば全ノードの状態が分かる
- 稼働時間帯（決定3）: 夜間に止めるlocationの稼働時間帯は、すでに基準値の設定にある。ノードごとに持つと、同じ値を2か所で入れることになり、食い違う
- 2窓（決定3）: 設計メモ2.2の「一定時間（例: 2窓 = 10分）データが来ないエリアは計測停止中にする」に合わせた。1窓だけの欠けは、送信の遅れでも起きる
- 状態が変わったときだけ（決定5）: 設計メモ2.3の提案。メールは停止と復旧の1回ずつで済み、ログがそのまま停止と復旧の記録になる。メールを送る仕組みを自前で持たずに済む
- `/aggregate`の停止（決定6）: 判定する処理が止まると、ノードの通知も止まる。ログの途絶えなら、Cloud Schedulerが止まった場合と、`/aggregate`が失敗し続ける場合の両方を拾える

## 検討した選択肢

| **選択肢** | **採用しなかった理由** |
|---|---|
| 管理画面で登録したノードだけを監視する | 登録を忘れると通知されない。#32の方針と合わない |
| `node_health_stats`を毎回遡って読み、監視するノードを決める | 集計のたびに、ノードの数×窓の数だけ読み取りが要る |
| 稼働時間帯をノードごとに`config/nodes`に持つ | 基準値の稼働時間帯と、同じ値を2か所で入れることになる |
| Cloud Monitoringだけで判定する（ノードごとのログが途絶えたら通知） | 稼働時間帯を考慮できず、夜に止めるノードで毎晩通知される |
| 止まっている間、窓ごとにログを出す | 停止と復旧の時刻が、記録としてまとまらない |
| `/health`への稼働時間チェック（設計メモ2.3の提案） | サービスが動いていれば通ってしまい、Cloud Schedulerの停止や、`/aggregate`の失敗を拾えない |

## 結果

- 集計1回につき、Firestoreの読み取りが増える（2のドキュメント、`config/baseline`、`config/nodes`）。書き込みは最大1回増える
- 一度も送ってこないノードは、監視されない
- 撤去済みにしたノードも、送ってくれば数える。最終受信時刻も更新するので、管理画面で「撤去済みなのに受信あり」と出せる
- サイネージの`stale`（locationの記録が15分より古い）と、ノードの停止の判定は別のまま。2台あるlocationで1台だけ止まると、通知は来るが`stale`にはならない。稼働時間帯の外でlocationのノードがすべて止まると、`stale`にはなるが通知は来ない

## 残っている課題

- ノードが1台だけ止まったlocationの台数は、そのまま減る。サイネージにどう出すか
- 設計メモ2.2の提案（サイネージの表示とアラートで、停止の判定を1か所にする）に合わせるか
- 「生きているが異常」の警告（昼間なのに0件が続く、NimBLEのキャッシュ上限128台に達した。設計メモ2.1）
- 停止と復旧の履歴をFirestoreに残し、稼働率を出す（設計メモ2.3）
- 稼働時間帯の始まりに、ノードの起動が遅れたときの扱い

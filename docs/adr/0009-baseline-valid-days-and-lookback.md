# 0009. 基準値は、有効な日をN日集めるまで遡って計算する

- ステータス: 採用（実装は`feature/max-devices-batch`にあり、2026-09-23時点で未マージ）
- 決定日: 2026-09-14
- 起票: chirushiyo
- 関連: #24, #23, #32, #35, ADR 0008（決定2の一部、決定3、決定4、`max_devices`のスキーマを置き換える）

## 背景

ADR 0008では、基準値を過去N週間（初期値4）の同じ曜日から計算するとしていた。大学のキャンパスが対象なので、母集団には長期休業、祝日、センサーの停止した日が混ざる。4週の固定の窓では、次の問題が起きる。

1. 低い値がp95を崩す: p95は順位で決まるので、休業日が混ざると、学期のデータの何%の位置を指すかがずれる。4日のうち3日が休業日なら、1日、3時間分がlevel 9の水準まで基準値が下がる
2. 壊れ方が片方向: 学期から休業に移るときは、学期の基準で全部level1になり正しい。休業から学期に戻るときは、休業の基準で全部level9になり壊れる。休み明けの1週目は、母集団の4日がすべて休業日になる
3. 欠測とゼロを見分けられない: 記録が無い理由がノードは動いていて誰もいなかったとノードが落ちていたの2つあり、区別できない。半日落ちた日は、残った半分のスロットだけで評価されて母集団を歪める
4. 学事暦を手で保守する前提は続かない: 担当は年度ごとに入れ替わる。毎年、学年暦から休業日を写す作業が律儀に続く前提は、2年目以降に崩れる

## 決定

1. 固定の窓をやめる。直近の同じ曜日から1週ずつ遡り、有効と判定した日だけを数え、N日（初期値4）そろった時点で打ち切る。そろったN日の稼働時間帯のスロットをまとめてp95を取る
2. 日ごとに2つのフィルターで判定する
   - 完全性: 稼働時間帯に記録のある1日を一定の分単位で区切った時間枠が、`180 × 0.8 = 144`以上。ノードの停止を弾く
   - 水準: その日の中央値が`refMedian × 0.5`以上。休業日を弾く。最大値ではなく中央値を使う（休業日でも一瞬は人が通るため）
3. `refMedian`は、フィルターを通していない全ての日から作る。直近26週の同じ曜日の、日ごとの中央値の中央値。(location, 曜日) ごとに作る
4. 12週遡ってもN日そろわなければ、`max_devices`を書き換えない（凍結）
5. `uniqueDeviceCount: 0`の記録を明示的に書き、記録が無いということはノードが落ちていたと一意に決まるようにする
6. 基準値を出す条件を`baseline >= 9`とする
7. 基準値を出さない場合は、何も書かない。一度も出していなければドキュメントが無いまま（`level: null`）、出したことがあれば古い値が残る（凍結）
8. `toLevel`は`MaxDeviceData | null`を受け取る
9. `max_devices`にp50とp05も保存する（今は計測だけで、判定には使わない）
10. フィルターで弾いた日を、理由と判定に使った数値とともに`excluded_records`に残す
11. 休日（`config/academic_calendar`）は任意の入力とし、無くても動く

## 理由

- 遡る方式にすると、失敗の向きが変わる: 4週の固定の窓では、休業のデータで基準値が計算され、休み明けに全部level 9になる。遡る方式では、有効な日が見つからずに前の学期の基準値のまま凍結される。基準が古いだけで、表示は壊れない。授業の再開日には、すでに学期の基準値が入っている
- `refMedian`を基準値から作らない: 今までのp95に入らない日を外す処理をそのまま実装すると、基準値はフィルターを通った日から計算され、フィルターはその基準値で判定する、という循環になる。人出が恒久的に減ったとき、毎日を異常に低いと弾き続け、古い賑わっていたデータを参照し続ける
- 26週: 中央値は少数派には動かされないが、多数派が入れ替わると逆転する。本学の最長の休業（春休み約7週、夏休み約8週）を当てはめると、26週なら休業のサンプルは31〜35% に収まる。12週では春休みの終わりに58% になり、フィルターが働かなくなる
- 曜日ごとの`refMedian`: 全曜日をまとめると、土日の中央値が常に閾値を下回り、週末の基準値が永久に計算できない
- 完全性のフィルターと0件の記録は一組: 0件の記録だけを先に入れると、休業日のゼロが母集団を膨らませる。フィルターだけを先に入れると、半日落ちた日が見分けられない。どちらを先にしても悪化するので、同時に入れる
- `baseline >= 9`: 1段の幅は`baseline / 9`台。これが1台を下回ると、整数の台数が段を飛び越える（`baseline = 4`ならlevel 1, 2, 4, 6, 8に届かない）。9は9段階が9段階として成り立つ最小の値で、設計から一意に決まる
- 上位側は外さない: 上位5% を外すと、p95がおおよそp90になるだけ。上振れへの強さは、issue #1で最大値ではなくp95を選んだ時点で入っている
- 学事暦を任意にできる: 決定1、4、6の組み合わせで、カレンダーが無い・古いときの最悪の場合が凍結になった。必須の入力を任意に変えたのではなく、失敗したときのコストを下げたことで任意にできるようになった

## 検討した選択肢

| **選択肢** | **採用しなかった理由** |
|---|---|
| 過去N週間の固定の窓（ADR 0008） | 休業日の混入で静かに劣化し、休み明けに壊れる |
| 学事暦だけに頼る | 担当が毎年入れ替わる体制で、毎年の手入力は続かない。崩れた瞬間に上と同じ壊れ方をする |
| 統計の判定だけにする | 長期の休業を新しい通常の時期と見分けられない。精度を上げる任意の入力として学事暦を残す |
| 基準値の下がり幅に上限を設ける | 日次で更新するため、7週の休業で49回下がる。1回2% でも累計で37% 下がる。効かせると学期中の正当な減少まで止めてしまう |
| 上位5% も外れ値として外す | p95がp90に変わるだけ |
| 弾いた日の記録を`excluded_records`にコピーする | `congestion_records`は消さないので二重管理になる |
| 日の最大値で判定する | 休業日でも一瞬は人が通るので、平常の日と見分けられない |
| `refMedian`の窓を12週にする | 春休みの終わりに休業が過半数になり、フィルターが働かなくなる |

## 結果

- 50% を超える恒久的な人出の減少があると、自動では戻らない。フィルターが新しい平常を弾き続け、遡りの上限に達して凍結する。`lookbackWeeks`が上限に張り付くことで気づけるが、人が手を入れるまで基準は古いまま
- 遡ると基準が古くなる。11週遡って集めた4日は、4週で集めた4日より新しさで劣る
- 完全性のフィルターの0.8と水準のフィルターの0.5には、まだ根拠が無い。`excluded_records`が1学期分溜まってから較正する
- 設置してすぐは有効な日がそろわず、しばらくlevelが出ない。デモなどでlevelを出すには、基準値を手で入れる必要がある

## 残っている課題

- 手入力の基準値が読めない: READMEの手順は手入力だと分かるよう`sampleDays: 0`とするよう記載されているが、`MaxDeviceSchema`は`sampleDays`と`sampleCount`に`positive()`を課している。READMEのとおりに入れると検証に失敗し、`getMaxDevice`が`null`を返して`level: null`のままになる。mainにも同じ食い違いがある
- ドキュメントIDの作り方が読み書きで違う: `saveMaxDevice`はlocationの使えない文字を`_`に置き換えてIDを作るが、`getMaxDevice`は置き換えずに読む。今のlocation（`cafeteria`, `bus_stop`）では差が出ないが、記号を含むlocationでは書いた基準値が読めない
- 0.8と0.5の較正（`excluded_records`が溜まってから）
- p95 / p50による、人の増減と無関係に見えているデバイスの判定（今は計測だけ）
- `computedAt`が古い基準値をAPIでどう扱うか
- `lookbackWeeks`が上限に張り付いたときの警告

# 0004. 全デバイスを保存し、数える対象は集計時に絞る。アクセサリーは数えない

- ステータス: 採用（フィルタの順序と構成はADR 0007で変更）
- 決定日: 2026-09-05
- 起票: chirushiyo
- 関連: #11, #1, ADR 0007

## 背景

1. 当時のスキーマ（`parsedDeviceSchema`）は`companyId`と`nearbyInfo`に`min(1)`を課していた。`parseRawData`はApple以外の端末や、Manufacturer Specific Dataの無いパケットで空文字列を返すため、Appleの本体端末以外は検証を通れず、保存されなかった
2. RSSIの閾値と同じく、Company IDで絞る方針も実測で確かめる必要がある。保存の時点でApple以外を落とすと、後から分布を見られず、ダッシュボードでも可視化できない
3. Apple Continuityのメッセージのうち、`0x07`（AirPods、Beats）と`0x12`（AirTag）は本体端末ではなく、人数として数えるべきでない

## 決定

1. 受信したデバイスは、メーカーを問わずすべて保存する。数える対象の絞り込みは、保存の時点ではなく集計の時点で行う
2. 数える条件は`companyId === "004C" && isNearbyInfo === true`とする
3. Apple Continuityのメッセージタイプは、許可リスト方式で`0x10`（Nearby Info）だけを通す
4. `parseRawData`の戻り値を、タプルから名前付きのオブジェクト（`{ companyId: string | null, isNearbyInfo: boolean }`）にする。「該当なし」を空文字列で表すのをやめ、値が無いことを型で表す

## 理由

- 保存前に落としたデータは、後から取り戻せない。絞り込みは集計の時点にしておけば、条件を変えても元のデータが残る
- 拒否リスト方式（`0x07`と`0x12`を弾く）では、知らないタイプが現れたときにアクセサリーが混ざる。許可リスト方式なら、知らないものは数えない側に倒れる
- タプルは位置で意味が決まるので、呼び出し側で取り違えやすい

## 検討した選択肢

| **選択肢** | **採用しなかった理由** |
|---|---|
| 保存の時点でAppleの本体端末に絞る（従来どおり） | 閾値や許可リストを後から検証できない |
| 拒否リスト方式でアクセサリーを弾く | 未知のタイプが観測されたときにアクセサリーが混入する |

## 結果

- `pending_scans`のドキュメントが大きくなる（全デバイスを保存するため）
- 分かっている限界:
  - Apple Watchも`0x10`を送るので、iPhoneと併用している人は2台に数えられる。`0x10`のペイロードから機種を見分ける公開された仕様は無い。実測で人数より明らかに多ければ見直す
  - Apple ContinuityのメッセージタイプはAppleの公開仕様ではなく、リバースエンジニアリングによる情報に基づく。将来変わる可能性がある
  - `0x10`の有無しか保存しないので、除外したアクセサリーの内訳は出せない

## 実装

- `f36822a` Nearby Info（`0x10`）のときだけ`true`を渡す形に変更（2026-09-06）
- `6ec2674`パース結果の受け取りをタプルからオブジェクトに変更
- `8c2490c` `companyId`が4文字のときだけ返し、それ以外は`null`
- `4f23af5` `companyId`と`isNearbyInfo`で数える対象かを判定する関数（2026-09-10）
- `7175319`, `c7142d9`スキーマとテストの追従（2026-09-11）

その後、ADR 0007で、フィルタの順序が「重複排除 → Company ID → RSSI」に変わり、許可リストは設定（`config/filter_pipeline`）で変えられるようになった。数える条件の既定値は、このADRのまま。

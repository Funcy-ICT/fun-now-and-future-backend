## 背景

バックエンドは当初、Node.js標準のHTTP APIとして書かれていた。ルーティング、リクエストの検証、レスポンスの整形をすべて手で書いており、実装済みのエンドポイントは数個だった。このまま増やすと、次の問題が見込まれた。

- リクエストとレスポンスの型をフロントエンドと共有できず、スキーマを変えたときに食い違う
- ESP32から届くペイロードの検証が手書きで、スキーマを一か所で管理できない

選定の時点で決まっていたこと、決まっていなかったことは次のとおり。

- 決まっていた: 表示層はReact。ESP32のデータはZodで検証する
- 決まっていなかった: 実行環境（Firebase FunctionsかCloud Runか。Cloudflare Workersも候補に挙がっていた）

体制は、バックエンド班3名、うちクラウド層の担当は1名。

## 決定

- 言語はNode.js（TypeScript）にする（2026-06-22にNotionに記載）
- フレームワークはHonoにする

## 理由

判断の基準は「チームの中でコードを読める人数を最大にする」こと。担当が1名の層は、その人が動けないと保守が止まる。担当外の人が読んで直せる状態にしておくことを、実行性能や言語の機能より優先した。

言語: 表示層（React）と言語がそろい、担当が分かれていても互いのコードを読める。型も追加のスキーマ層を挟まずに共有できる。起動が軽く、リクエストごとにインスタンスが起動しうる実行環境の候補と合う。

フレームワーク（Hono）:

1. RPC（`hc<AppType>`）で、ルートの入出力の型をフロントエンドから直接参照できる
2. `@hono/zod-validator`で、検証のスキーマと型を1つのZodスキーマから作れる
3. `c.req.json()` / `c.json()`が`fetch` / `Response`とほぼ同じ形で、表示層の担当者に読みやすい。Expressの`req` / `res`はNode.js独自の概念で、新しく覚える必要がある
4. CORS、ロガー、JWTなどが本体に含まれ、追いかける依存パッケージが少ない
5. （補助的な理由）Web標準に沿っていて、Node.js、Cloudflare Workers、Deno、Bunのどれでもそのまま動く。実行環境が決まっていない段階での保険

## 検討した選択肢

| **選択肢** | **採用しなかった理由** |
|---|---|
| Go / Rust | バックエンド班に慣れた人がいない。実行環境が決まらないうちに言語の習得も並行するのは現実的でない |
| Java（Spring Boot） | Javaが読めることとSpringのコードが読めることは別。JVMの起動時間が、リクエストごとに起動しうる実行環境と合わない。規模に対して構成が強制され、実装が重い |
| Python（FastAPI） | 有力だったが、フロントエンドとの型共有がOpenAPI経由の間接的なものになる。言語が分かれ、互いに読める人数が減る |
| Express | 型が後付けで、フロントエンドとの型共有を標準で持たない。Node.js以外で動かすには互換機能が要る |
| NestJS | DI、デコレータ、モジュールを先に覚えないと読めない。規模に対して構成が強制され、実装が重い |
| Fastify | サーバー側の型推論は強いが、フロントエンドへ型を渡す手段は持たない。Node.jsが前提で、候補だったCloudflare Workersでそのまま動かない |

## 結果

- 良かった点: Cloud Runへの移行（ADR 0002）で、ルートの定義を書き換えずに済んだ。`app.request()`でサーバーを起動せずにテストが書けることは、選定の後に分かった利点
- 引き受けたこと: Expressに比べて事例が少なく、困ったときの情報が見つけにくい。比較的新しく、破壊的変更の心配がある。機能が本体にまとまっているので、本体の更新が全体に影響する

## 残っている課題

- フロントエンドがJavaScriptのままで、RPCによる型共有の利点をまだ受けられていない。TypeScriptへの移行が必要
- 今後の技術選定は、決めた時点でissueに残す（このADRが事後記録になった反省）

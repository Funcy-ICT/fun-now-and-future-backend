# 0003. 受信データはPOST 1回分を1ドキュメントにまとめて保存する

- ステータス: 採用（保存の経路はADR 0010で変わったが、この判断は有効）
- 決定日: 2026-08-06
- 起票: chirushiyo
- 関連: #1, ADR 0010

## 背景

ESP32は数分に一度、スキャンしたMACアドレスを配列にまとめてPOSTしてくる。これを、5分ごとの集計（`/aggregate`）までの間、Firestoreの`pending_scans`に一時的に置く。

混雑時には1回のPOSTに数百〜1000台規模のデバイスが含まれる可能性がある。

## 決定

1回のPOSTを丸ごと1ドキュメントとして保存し、デバイスは配列のフィールドとして持たせる。MACアドレス1件ごとに1ドキュメントにはしない。

## 理由

Firestoreの料金とスループットは、ドキュメントの件数で決まる。MAC 1件ごとに保存すると、混雑時は1回のPOSTで1000件規模の書き込みになる。POSTごとにまとめれば、書き込みの件数はPOSTの回数に比例するだけで済む。

## 検討した選択肢

| **選択肢** | **採用しなかった理由** |
|---|---|
| MACアドレス1件ごとに1ドキュメント | 書き込みの件数が台数に比例し、料金とスループットの両面で不利 |

## 結果

- 書き込みは、ノードの数 × POSTの頻度で見積もれる
- 1ドキュメントの上限（1MiB）に気をつける必要がある。受信側で`devices`の件数に上限（256台）を設けた（`90c2768`。NimBLEのキャッシュ上限128台に余裕を見た値）

## 実装

- 当初は受信エンドポイントが直接`pending_scans`に書いていた（`savePendingScan`）
- ADR 0010で、受信 → Pub/Sub → 処理側、の経路に変わった。処理側（`savePendingScanEvent`）も、1メッセージ（= POST 1回分）を1ドキュメントとして保存しており、この判断はそのまま生きている
- ドキュメントIDは、当初の自動採番から、`sendId`（無ければPub/Subの`messageId`）で決める形に変わった。同じメッセージが2回届いても二重に数えないため（`bfe1e4b`）

# 0010. 生データはPub/Sub経由でBigQueryに貯め、表示用の値だけをFirestoreに置く

- ステータス: 採用
- 決定日: 2026-09-20
- 起票: chirushiyo
- 関連: #36, #37, #38, #39, #40, #41, PR #42, PR #43, ADR 0003, ADR 0007

## 背景

ESP32の生データは`pending_scans`に一時的に置かれ、`/aggregate`のたびに削除されていた。そのため、次のことができなかった。

- 生データを長く残して分析する
- フィルタの設定（許可リスト、RSSIの閾値）を変えたときに、過去の分を新しい設定で計算し直す

ADR 0007の`scan_diagnostics`は、診断モードが有効な期間の、重複排除の後のデータしか残らない。

想定する量は、ノード約10台がそれぞれ1分ごとにPOSTする程度。

## 決定

1. 受信のエンドポイントは、認証、検証、MACの正規化とハッシュ化、`rawData`の解析、受信時刻の付与を行い、Pub/Subのトピック（1つ）にpublishする。publishの完了を待ってから200を返す
2. トピックには2つのサブスクリプションを付ける
   - BigQueryサブスクリプション → テーブル`scan_events`（集計せずにそのまま入れる）
   - プッシュ → 処理側のサービス → Firestoreの`pending_scans` → `/aggregate`（5分ごと）→ `congestion_records`
3. Firestoreには、表示に使う結果（`congestion_records`, `max_devices`）と設定だけを長く置く。`pending_scans`は集計したら消す
4. MACアドレスは、受信の時点でHMAC-SHA256にする。鍵は固定でSecret Managerに置き、`hashKeyVersion`（`v1`）を記録して将来の鍵の交換に備える。ハッシュにする前に、区切り文字と大文字小文字をそろえる。アドレスの種別（ランダムの種類）は、ハッシュにする前に上位2ビットから推定して残す
5. 同じコードから、環境変数`SERVICE_ROLE`で2つのサービスに分けてデプロイする
   - `ingest`（公開）: `/receiveSensorData`、サイネージ用のルート、`/health`
   - `worker`（Cloud Runの認証必須。Pub/SubとCloud Schedulerのサービスアカウントだけが呼べる）: `/pubsub/scan-events`、`/aggregate`、`/internal/batch/*`
6. 集計の窓は、ESP32の時刻ではなく受信時刻で決める

BigQueryの設定（メモでの決定。コードの外）:

- データセットは東京リージョン（`asia-northeast1`）
- `scan_events`は受信時刻で日ごとにパーティションを切り、`location`と`nodeId`でクラスタリングする。クエリにパーティションの指定を必須にする
- `rawData`を含め、取れるデータはすべて残す。保持期間の初期値は無期限（管理画面から変えられるようにする: #40）
- 閲覧できるのは、設計者とバックエンドのサービスアカウントだけ

## 理由

- 保存の費用: ハッシュにした生データをFirestoreに溜め続けると、書き込み、読み取り、保存のすべてに費用がかかり、集計のたびの読み取りも膨らむ。BigQueryは保存が安く、分析のクエリも月1TiBまで無料。Firestoreには、サイネージが頻繁に読む小さなデータだけを置く
- 計算し直すには元のデータが要る: 設定を変えたとき、元のデータが残っていなければ過去の分を計算し直せない。`pending_scans`は集計の後に消えるので、計算し直せるのはBigQueryの生データからだけになる（#41）
- 分析の方法を縛らない: BigQueryの上でSQLで分析しても、取り出して手元で分析してもよい。どちらも元のデータが残っていることが前提
- Pub/Subを挟む: BigQueryサブスクリプションを使えば、BigQueryへの書き込みや再試行のコードを書かずに済む。1つのトピックから、BigQueryと集計の2か所に配れる。処理側が止まっても受信は成功し続け、メッセージはPub/Subに残り、直った後に届く
- HMACにする: MACは48ビットしかなく、素のSHA-256では総当たりで元に戻せる
- サービスを分ける: Cloud Runの認証はサービス単位でかかる。公開しなければならない受信側と、特定のサービスアカウントだけに呼ばせたい処理側を分けると、認証をコードに書かずにIAMで守れる
- 受信時刻で窓を決める: ESP32の時刻は信用できない。処理側で`serverTimestamp()`を使うと、Pub/Subで遅れた分だけ時刻がずれる

## 検討した選択肢

| **選択肢** | **採用しなかった理由** |
|---|---|
| 生データをFirestoreに溜め続ける | 保存と読み取りの費用が膨らむ |
| `/aggregate`からBigQueryに書く（メモの案C） | BigQueryへの蓄積が /aggregateの成否に縛られ、集計で読まれなかったデータも入らず、3.6で /aggregateが無くなれば作り直しになる |
| 処理側から別のトピックへpublishし直す（メモの案D） | 1通を2回publishしてトピックも増えるうえ、得られるのは受信を薄く保てることだけである |
| 受信のエンドポイントでBigQueryとFirestoreの両方に直接書く | （このADRの作成時に補った比較）片方だけ成功した場合の扱いと再試行を自前で書く必要がある |

## 結果

- 受信のエンドポイントは、publishに失敗したら500を返し、ESP32に再送させる。200を返したデータはPub/Subに届いている
- 同じメッセージが2回届いても二重に数えないよう、`pending_scans`のドキュメントIDを`sendId`（無ければ`messageId`）から決め、上書きで保存する
- 処理側への不正なメッセージには400を返す。再試行の後にデッドレターに入り、件数のアラートで気づける
- 集計は窓が閉じた60秒後に行い（Cloud Schedulerは`1-59/5 * * * *`）、Pub/Sub経由で遅れてFirestoreに書かれるデータを待つ。窓に間に合わなかったデータは24時間後に消す
- 受信側は、`MAC_HASH_KEY`と`SCAN_EVENTS_TOPIC`が未設定なら起動に失敗する。設定漏れのままデプロイされても、古いリビジョンが動き続ける
- `SERVICE_ROLE`の綴りを間違えて全部のルートが公開されないよう、知らない値は例外にする。未設定なら全部のルートが載る（ローカルとテスト用）
- この構成より前の窓は、計算し直せない（`pending_scans`は消えている）
- TypeScriptの集計とBigQueryのSQLが二重実装になる。突き合わせのテストで食い違いを防ぐ（#39）

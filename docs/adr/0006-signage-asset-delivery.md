# 0006. 広報アセットは公開バケットから直接配り、APIは一覧だけを返す

- ステータス: 採用
- 決定日: 2026-09-13
- 起票: chirushiyo
- 関連: #20, PR #21

## 背景

サイネージに掲示する広報アセット（画像、PDF）を配信する。投稿と承認の流れは対象外で、承認済みのアセットを配る経路だけを作る。

サイネージに出す画像は、画面に出た時点で通行人全員が見る。秘匿する必要は無く、配信の経路に認証や失効の仕組みを置いても守るものが無い。

## 決定

1. アセットの実体は、Cloud Storageの公開バケットの`objects/{uuid}`に置き、サイネージはそこから直接取得する
2. 公開バケットには`allUsers`に`roles/storage.legacyObjectReader`だけを付ける。`roles/storage.objectViewer`は使わない
3. API（`GET /signage/assets`）は、掲載中のアセットの一覧（ID、題名、種類、URL、掲載終了日時）だけを返す。実体を返すエンドポイントは作らない
4. アセットの情報はFirestoreの`prAssets/{id}`に置く。`status`は後の段階の値も含めて`pending | approved | rejected | revoked`と定義し、今は`approved`だけを読む
5. 掲載期間の判定はアプリ側で行う。Firestoreのクエリは`status == 'approved'`だけで引く
6. 認証は、既存のセンサー用のヘッダーキーの照合を流用し、`/signage/assets`にだけかける

## 理由

- `objectViewer`にはオブジェクトの一覧を見る権限が含まれ、バケットのルートのURLから全オブジェクトを列挙できてしまう。UUIDを推測できない名前にした意味が無くなる
- 掲載期間の判定は一覧の側で完結するので、実体の配信をCloud Run経由にしても分岐が空振りする
- `publishUntil`に範囲の条件をかけると、`null`（無期限）のドキュメントが比較から外れて一覧に出なくなる。件数が数百に届くまでは、メモリ上で絞っても十分速い
- `status`の値を先に定義しておけば、後から投稿や承認の流れを足しても移行が要らない（値を足すだけ）

## 検討した選択肢

| **選択肢** | **採用しなかった理由** |
|---|---|
| Firestoreに実体を入れる | ドキュメントの上限1MiBに対し、Base64で約1.33倍に膨らみ、元のファイルは700KB台が上限。Content-Typeを付けて返せない |
| Cloud Runでバイト列を中継する | 掲載期間の判定は一覧で済むので、中継しても意味が無い。ログと独自のエラーページのためだけにストリーミングの実装を抱える |
| 署名付きURL | 静止画は取得された時点で複製が相手に渡るので、URLの失効に意味が無い |

## 結果

- 取り下げるときは、Firestoreの`status`を変えるだけでは直リンクが生きたまま。Cloud Storageのオブジェクト自体を削除する運用にする
- 公開バケットと非公開バケットを分けるまでは、未承認や却下のアセットも同じ公開バケットに置かれる可能性がある（`status`はFirestore側の見え方を制御するだけで、Cloud Storageのアクセス制御ではない）
- Firestoreから読んだドキュメントは、必ずZodで検証してから使う。登録の手段ができるまでは手で作ったドキュメントが混ざるため

後の段階に回したこと: 投稿と登録（Webダッシュボード）、EXIFの除去（GPS座標の残った写真を公開しないため）、承認の流れと承認者の記録、掲載許諾の記録、認証のヘッダーキーからFirebase Authenticationへの移行、公開と非公開のバケットの分離。

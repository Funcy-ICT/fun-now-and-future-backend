# 0013. RSSIの閾値をノードごとに持ち、どれか1つのノードで閾値を通った端末を数える

- ステータス: 採用（分析用のSQLは未実装）
- 決定日: 2026-10-11
- 起票: chirushiyo
- 関連: ADR 0007（決定1の代表の選び方と、残っている課題「重複排除が先頭であることの検証」）, ADR 0012, ADR 0014, #22, #41

## 背景

RSSIの閾値は、`config/filter_pipeline`の`rssiFilter.rssiThreshold`の1つだけで、全ノードに同じ値を当てている（既定は-100で、実際には絞っていない）。同じ距離でも、ノードの置き場所、高さ、向き、遮蔽物でRSSIは変わるので、閾値はノードごとに決める必要がある。

今の実装では、ノードごとの閾値を当てられない。

- `/aggregate`は、フィルタを通す前に`groupByLocation`でlocationごとに検出をまとめる。この時点で`nodeId`が落ちる
- `dedupeByMac`は、同じMACの検出のうち、RSSIが最も強い1件だけを代表として残す。分析用のSQLの`dedupe`も同じ（`services/analysis_sql.ts`）

代表の1件に、そのノードの閾値を当てると、ほかのノードで通るはずの端末を落とす。

```
閾値: ノードA -65、ノードB -75
端末h2: Aで-70、Bで-72を検出
代表はAの-70。Aの閾値-65に届かないので落ちる。Bの閾値-75なら通る
```

また、ADR 0007は、`scan_diagnostics`にどのフィルタもかける前の端末が残るよう、重複排除を先頭にした。先頭であることの検証は、残っている課題だった。

## 決定

1. 同じlocationの同じ端末を複数のノードが検出したとき、どれか1つの検出が、そのノードの閾値以上なら、その端末を残す
2. 閾値は`rssiFilter`に持たせる。今の`rssiThreshold`は名前を変えずに残し、`nodeThresholds`（location → `nodeId` → 閾値）に無いノードに使う。キーをlocationと`nodeId`の組にするのは、ノードを別の場所に移したとき、前の場所の閾値を使わず、未校正として目立たせるため（設計メモ2.6の提案）。`nodeThresholds`は任意の項目にし、既定値（`{}`）を付けない
3. 重複排除は先頭に必須とする。管理画面から保存するときに、「`dedupe`が先頭にある」「同じ段は1回だけ」を検証する
4. 重複排除は、端末ごとに、すべての検出（`nodeId`、RSSI）を持つ。代表の1件に絞らない
5. `scan_diagnostics`の端末に、ノードごとの検出（`nodeId`、RSSI）を足す
6. 分析用のSQLも、同じ判定にする
7. ノードごとに変える設定のうち、台数に影響するものは、RSSIの閾値だけにする

## 理由

- 数え方（決定1）: 設計メモ2.8の提案「location内のどれかのノードで条件を満たしたMACを1台と数える」と同じ。人が2つのノードの間にいるとき、近い方のノードで見えていれば数える
- 重複排除を先頭に残す（決定3、4）: `scan_diagnostics`には、重複排除の直後の端末が残る（ADR 0007）。先頭なら閾値を下回った端末も残り、「このノードの閾値を下げたら何台増えるか」を、BigQueryの保持期間を超えて確かめられる（ADR 0012）
- 重複排除を必須にする: 各ノードは5分の窓に約5回送るので、重複排除が無いと同じ端末を何度も数える
- すべての検出を残す（決定4）: 代表の1件では、決定1の判定ができない（背景の例）。検出が残っていれば、`rssiFilter`は段の位置に関係なく同じ台数を出す。設計メモ2.6で決めた「k回以上」の条件も、重複排除のあとに置ける
- 名前を変えない、既定値を付けない（決定2）: `configHash`は`stages`のJSONから作る（`services/filter_config.ts`）。名前を変えたり、読むときに`{}`を足したりすると、設定の中身が同じでもハッシュが変わる。ハッシュは、`aggregate_runs`と、設定変更時の再計算（#41）の手がかりになる
- `config/filter_pipeline`に置く（決定2、7）: 台数に影響する設定は、`configHash`と再計算の対象に入っている必要がある

## 検討した選択肢

| **選択肢** | **採用しなかった理由** |
|---|---|
| RSSIの判定を、重複排除の前に置く | 台数は合うが、`scan_diagnostics`に閾値を下回った端末が残らない。ADR 0007の順序とも食い違う |
| 代表の1件に、そのノードの閾値を当てる（今の形のまま） | 代表のノードの閾値しか効かない（背景の例） |
| RSSIからそのノードの閾値を引いた値が最大の検出を、代表にする | 台数は合うが、重複排除がRSSIの段の設定を知る必要があり、段どうしが独立しなくなる |
| `rssiThreshold`を`defaultThreshold`に改名する | 同じ設定でも`configHash`が変わる。`analysis_sql.ts`も直す必要がある |
| 閾値を`config/nodes`に置く | `configHash`に入らず、再計算の対象から漏れる |
| ノードごとに「集計から外す」設定を持つ | 必要な場面が、重複排除とノードごとの閾値で足りる。外したいときは、閾値を実際には出ない値（0など）にすればよい |
| 閾値のキーを`nodeId`だけにする | ノードを移したとき、前の場所に合わせた閾値が、そのまま使われる |
| `nodeId`とlocationの対応をサーバーで持つ | ノードが少なく、ESP32の設定で足りる |

## 結果

- 変更の範囲が広い: `/aggregate`のパイプラインの型、`dedupeByMac`の戻り値、`scan_diagnostics`のスキーマ、分析用のSQLと突き合わせテスト
- `scan_diagnostics`の1件が大きくなる（端末ごとに、検出したノードの数だけ要素が増える）。前の形のドキュメントも残る
- 管理画面では、重複排除を外すことも動かすこともできない。並べ替えられるのは、Company IDとRSSIの段だけになる。どちらを先にしても台数は同じで、段ごとの通過数だけが変わる
- Firestoreコンソールで入れた設定は、決定3の検証を通らない。読む側は今のまま寛容に動く（ADR 0014）
- 判定の実装が入るまでは、管理画面から`nodeThresholds`を保存できないようにする（保存しても集計に使われないため）

## 残っている課題

- 「k回以上」の条件（設計メモ2.6）を入れるときの、検出回数の数え方（ノードをまたいで数えるか）
- 閾値を決める材料（ノードごとのRSSIの分布）は、BigQueryから出す（ADR 0012）

## 実装

- `0210c08` パイプラインの型`PipelineDevice`。重複排除で、端末ごとにすべての検出（`nodeId`、RSSI）を残す（決定4、#76）
- `46eb635` `rssiFilter`の`nodeThresholds`のスキーマ（決定2、#77）
- `e82d336` 管理画面から保存するときの検証。`dedupe`が先頭、同じ段は1回だけ、空でない`nodeThresholds`は拒否（決定3、#77）
- `db073ac`、`992ef9e` ノードごとの閾値での判定。閾値はlocation → `nodeId`で引く（決定1、2、#83）
- `a0d8d2a` `scan_diagnostics`の端末の検出`detections`（決定5、#83）
- 分析用のSQL（決定6）は未実装。それまでは、管理画面から`nodeThresholds`を保存できない

# 0014. 管理画面から変える設定に、versionと変更の履歴を持たせる

- ステータス: 採用（一部実装）
- 決定日: 2026-10-11
- 起票: chirushiyo
- 関連: #40, #41, PR #48, ADR 0007, ADR 0009, ADR 0012, ADR 0013, ADR 0015

## 背景

管理画面から、次の4つの設定を変えられるようにする。

| **ドキュメント** | **中身** | **読む処理** |
|---|---|---|
| `config/filter_pipeline` | フィルタの段（順番と値）、診断モード | `/aggregate`（5分ごと） |
| `config/baseline` | 基準値の計算の設定（全体と、locationごとの上書き） | 基準値のバッチ（毎日） |
| `config/retention` | BigQueryの保持期間 | 保存のときにBigQueryへ反映する |
| `config/nodes` | ノードの表示名と、撤去済みの印（ADR 0015） | `/aggregate` |

今は、どれもFirestoreコンソールで書き換えていて、次の問題がある。

- 誰がいつ何を変えたかが残らない。設計メモ2.4で、操作の履歴を残すと決めていた（#40の「認証のあとにやること」にもある）
- 2人が同時に変えると、後から保存した方が、何も言わずに上書きする
- 読む側は、値がおかしくても止まらないように、寛容に作ってある。フィルタの設定は、検証に通らないと、何も言わずに既定の構成で動く（`getFilterPipelineConfig`）。基準値の設定は、おかしい項目だけを捨てる

## 決定

1. 4つの設定のドキュメントに、値と同じ階層で`version`、`updatedAt`、`updatedBy`を置く。`version`が無いドキュメントは0とみなす。`updatedBy`は、認証が入るまでnull
2. 保存は、1つのトランザクションで行う
   1. 今の`version`が、画面から送られた`expectedVersion`と一致するか確かめる。違えば409を返す
   2. 値を書き、`version`を1つ増やす
   3. `config_history/{設定名}__{version}`に、変更の前と後の値、日時、変更した人を足す。`create`で書き、同じIDがあれば失敗させる
3. 履歴の前後の値は、検証せずに、保存したときの形のまま残す。フィルタの設定では、`configHash`も残す
4. 検証は、保存するときに厳しくし（範囲外の値、知らない項目、段の順番）、400を返す。読む側は今のまま寛容にする
5. 画面から受け取らない項目（`debugModeEnabled`）は、サーバーが今の値を引き継ぐ。無ければfalseにする
6. フィルタの設定の取得では、保存された値で動いているか、既定の構成で動いているか（`source`）と、今の`configHash`を返す
7. 保持期間は、「BigQueryに反映してから保存する」順番を保つ。`version`はDDLの前と保存のときの2回確かめる。保存のときに食い違ったら、Firestoreに残っている値でDDLをやり直してから409を返す
8. ルートは設定ごとに分ける。認証とロールの確認が入るまで、ルートは作らない。それまでは、スキーマと保存の処理だけを作る
9. 管理画面を使い始めたら、設定をFirestoreコンソールで変えない

## 理由

- 1つのトランザクション（決定2）: 値と履歴の片方だけが書かれることがない。`version`の確認と書き込みの間に、別の保存が割り込まない。#41の再計算のリクエスト（`config/recompute_request`）も、同じトランザクションで書ける
- 前後の値を検証しない（決定3）: 段の種類やパラメータは、後から増えたり変わったりする。古い形の履歴も読めるようにする。前の値も残すのは、コンソールで入れていた最初の値も記録するため
- 保存は厳しく、読む側は寛容に（決定4）: 画面からの打ち間違いは、保存の時点で止める。コンソールで入れた値で集計が止まるのは避ける（今の読む側の方針と同じ）
- 引き継ぐ（決定5）: `FilterPipelineConfigSchema`では`debugModeEnabled`が必須。画面から`stages`だけで上書きすると、この項目が消え、`/aggregate`が何も言わずに既定の構成で動く
- `source`を返す（決定6）: 検証に通らない値が保存されていても、画面からは分からないため
- 保持期間（決定7）: BigQueryのDDLは、Firestoreのトランザクションに入れられない。BigQueryに先に反映する順番は、#40の決定（Firestoreには、最後に反映できた値を残す）
- ルートを分ける（決定8）: Hono RPCで、設定ごとの値の型を管理画面に渡せる。認証の前にルートを作らないのは、リポジトリが公開されていて、誰でも設定を変えられてしまうため（#40と同じ）

## 検討した選択肢

| **選択肢** | **採用しなかった理由** |
|---|---|
| `version`を持たず、後から保存した方を勝ちにする | 同時に変えたとき、何も言わずに上書きされる |
| 値と`version`などを別のドキュメントに置く | 読む側が2つ読む必要がある。読む側のスキーマは知らない項目を無視するので、同じドキュメントでも困らない |
| 履歴に、変更の後の値だけを残す | 最初の変更の前の値（コンソールで入れた値）が残らない |
| 履歴をBigQueryに置く | 件数が少なく、管理画面ですぐ読みたい。`aggregate_runs`の`stagesJson`は窓ごとに使った設定で、誰が変えたかは持たない |
| `debugModeEnabled`も画面から受け取る | 画面に出さない項目なので（ADR 0012）、送り忘れると消える |
| `/admin/config/:name`のように、1つのルートにまとめる | Hono RPCで、値の型が設定ごとに分かれない |

## 結果

- 設定を1回保存すると、書き込みが2回になる
- Firestoreコンソールで直接変えた分は、`version`も履歴も変わらない
- #38で作らないとした`filter_configs`（`configHash`から設定を引くためのもの）とは目的が違う。ただ、履歴に`configHash`と値が残るので、結果として引けるようにはなる
- 保持期間は、409を返すまでの短い間、BigQueryとFirestoreの値が食い違う

## 残っている課題

- ロールの確認（設計メモ2.4: 「広報を承認できる人」と「閾値やデバイス設定を変えられる人」を分ける）。認証のissueで決める
- 管理画面のルートを、どのCloud Runのサービスに載せるか。今の`SERVICE_ROLE`は`ingest`（公開）と`worker`（Pub/SubとCloud Schedulerだけが呼べる）の2つで、どちらにも合わない
- 履歴の保持期間
